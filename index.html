Core properties

Fast enough to matter. Simple enough to trust.

The package stays deliberately Go-native: generic typed slices, fixed capacity, explicit reset semantics, and focused helpers for concurrent and request-scoped workloads.

01 / typed storage

No unsafe.Pointer

MemoryArena[T] is backed by []T. The compiler keeps allocation and access type-safe while values remain directly addressable inside the arena buffer.

02 / reuse

Reset the scope

Clear only the allocated region, move the offset back to zero, and reuse the original backing storage.

03 / slabs

Contiguous allocation

Reserve capacity-bounded slices with AllocSlab or copy values in with AllocSlabWith.

04 / explicit capacity

Panicking and Try* APIs

Use compact panicking methods on invariant-backed hot paths, or choose non-panicking variants when capacity exhaustion is part of normal control flow.

05 / integration

Context and HTTP helpers

Inject and extract typed arenas from context.Context or cloned *http.Request values.

Quick start

Allocate. Use. Reset.

Arena ownership stays visible in ordinary Go code. There is no custom compiler, CGo boundary, or hidden runtime.

01
Create a fixed-size arenaPick a concrete type and capacity for the scoped workload.
02
Allocate values or slabsReturned pointers and slices refer directly to the backing buffer.
03
Reset after the scope endsOld pointers and slabs are invalid once the arena is reset.
main.go Go 
package main

import (
  "fmt"

  "github.com/Protocol-Lattice/memoryArena"
)

func main() {
  arena := memoryArena.NewMemoryArena[int](4)

  first := arena.Alloc(10)
  batch := arena.AllocSlabWith(20, 30)

  fmt.Println(*first, batch) // 10 [20 30]
  fmt.Println(arena.Remaining()) // 1

  arena.Reset()

  next, ok := arena.TryAlloc(40)
  if !ok {
    return
  }

  fmt.Println(*next) // 40
}
Allocation models

Choose ownership before synchronization.

The fastest shared state is state you do not share. Start with a single-owner arena, use pooled arenas for per-task isolation, and reach for the synchronized variant only when multiple goroutines must allocate from one buffer.

MemoryArena[T]

Single owner

Minimal allocation overhead for one goroutine or one clearly owned execution path.

  • No synchronization
  • Values and contiguous slabs
  • Best for parsers, loops, and local scratch space
PooledMemoryArena[T]

Per-task isolation

Each Execute call checks out an isolated arena from sync.Pool, then resets and returns it.

  • Low contention across goroutines
  • Panic-safe reset
  • Best for requests, workers, and scoped jobs
ConcurrentMemoryArena[T]

Shared buffer

A semaphore gate serializes allocation and reset operations when multiple goroutines must share one arena.

  • Context-aware gate acquisition
  • Shared capacity accounting
  • Synchronizes allocation, not later pointer access

Good fit

Temporary data with one clear finish line.

An arena pays off when many values can be reclaimed together. It is a poor fit when individual objects must outlive the scope, capacity is unbounded, or ordinary heap allocation is already clear and fast enough.

Parsing

AST nodes and token batches

Build short-lived typed structures during one parse pass, then reset the entire scratch scope.

HTTP

Request-scoped buffers

Use a pooled arena per handler invocation so temporary values never compete for one shared lock.

Simulation

Tick-local working sets

Reuse memory between ticks when intermediate state becomes invalid at the same boundary.

Batching

Worker scratch memory

Allocate contiguous slabs for one batch, process them, and return the arena after the job completes.

Lifetime rules

Simple invariants. Sharp boundaries.

memoryArena stays safe by keeping ownership explicit. The package avoids raw memory tricks, but callers still need to respect reset-based lifetimes and concurrency boundaries.

01
Do not use values after Reset.

Old pointers and slabs still refer to the backing buffer, but their previous values are no longer live.

02
Keep pooled values inside Execute.

The arena resets before it returns to the pool, so allocated pointers and slices must not escape the closure.

03
Synchronize access after allocation.

The concurrent arena protects allocation and reset. It does not protect later reads or writes through returned pointers.

04
Size fixed capacity deliberately.

Use worst-case workload knowledge or the non-panicking Try* APIs when exhaustion is expected.
